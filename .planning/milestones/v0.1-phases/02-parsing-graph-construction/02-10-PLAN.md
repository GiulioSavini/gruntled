Planning-time evidence (probe over hcl v2.25.0, go1.27.0, linux/amd64, no -race; ParseConfig followed by hclsyntax.Walk):
| shape (inside `a = ...`) | fine at | fatal stack overflow at |
|---|---|---|
| `(((...1...)))` | 30k levels | 150k levels, and ~2M levels (the 4 MiB case) |
| `!!!...true` / `---...1` | 60k | 300k |
| `"${"${...}"}"` template nest | 12k | 60k |
| `[for v in x : [for ...]]` | 6.6k | 66k |
| `b { b { ... } }` blocks | 150k | 4 MiB worth |
| JSON `{"a":{"a":...}}` (hcl/json.Parse) | 50k | 4 MiB worth |
| ternary chains (`x ? 1 : x ? ...`, `x ? x ? ... : 2`) and `x + x + ...` | 4 MiB, no crash | none |
So recursion comes only from brackets, template/heredoc/quote nesting and unary operators. MaxNestingDepth = 1000 leaves at least 12x headroom under the smallest crash point (the race detector's larger frames included), and no hand-written HCL nests anywhere near 1000.
Memory note: `hclsyntax.LexConfig` used about 1.4 GB RSS on a 4 MiB single-character-token input. ParseConfig lexes the whole file the same way first, so the pre-scan does not raise the peak ParseConfig already has. For the same reason, tests use ~200k-level inputs (a few hundred KB) and never a 4 MiB token stream. The size-cap test stays cheap because MapFS reports the size and the file is refused before it is read.

Why the lexer and not a hand-written byte scanner: HCL's lexing rules are subtle. A quoted string does NOT end at a newline, heredoc markers are compared after bytes.TrimSpace and only at the start of a line, and `$${`/`%%{` are escapes. A hand-rolled scanner that disagreed with ragel on any of these could skip real code and under-count, and an under-count is exactly the crash this plan prevents. hclsyntax.LexConfig IS the parser's tokenizer, so it is exact by construction and never recurses (it lexed a 4 MiB `!` run without trouble). JSON has a trivial string rule (verified in hcl/v2/json/scanner.go scanString: a backslash toggles escaping, an unescaped `"` ends the string, and so does any byte < 0x20, which is NOT consumed), so a byte scanner that mirrors it exactly is used there.

API to create (02-11 depends on these exact names):
```go
package hclconv
const MaxFileBytes = 4 << 20      // 4 MiB
const MaxNestingDepth = 1000
var ErrFileTooLarge = errors.New("hclconv: file exceeds MaxFileBytes")
var ErrNestingTooDeep = errors.New("hclconv: nesting exceeds MaxNestingDepth")
// ReadFileLimited: fs.Stat(name) (a Stat error is returned as-is); Size() > MaxFileBytes -> ErrFileTooLarge without reading;
// then fs.ReadFile(name) (exactly one ReadFile call, so the terragrunt countingFS/readFailFS tests keep their meaning);
// len(src) > MaxFileBytes -> ErrFileTooLarge.
func ReadFileLimited(fsys fs.FS, name string) ([]byte, error)
func CheckNativeDepth(src []byte) error // HCL native syntax (.hcl, .tf, .tofu)
func CheckJSONDepth(src []byte) error   // .tf.json, .tofu.json
```
