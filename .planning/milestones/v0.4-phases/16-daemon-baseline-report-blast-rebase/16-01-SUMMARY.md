# Phase 16 Plan 01: IPC Protocol v2 Summary

**The daemon protocol is now v2. The server checks the version first, then decodes the request strictly and requires it to be byte-equal to its canonical encoding. Report responses never carry the blast view, blast responses carry no check bytes, and rebase reaches a `Handler`. Every refusal is a typed `*RefusedError`. A missing or empty blast view, or a rebase without a result, is an error and never a zero value. The blast response line is encoded once per snapshot by `Seal`: 20 requests against a 2.8 MB sealed line allocate 25 KB. Rebase failures after the request was sent are `ErrOutcomeUnknown`. A frozen verbatim copy of v0.3.0's respond and dump reader proves the version-mismatch matrix in both directions. With the version read as 1, the report line is byte-equal to v0.3.0's.**

## Accomplishments

### Task 1: v2 wire types, strict request, per-op respond, typed decode (ipc.go)
- **Constants:** `ProtocolVersion = 2` (:29), `OpBlast` and `OpRebase`, and the nine `Code*` constants (:59). `responseCap` (:72) defaults to `maxResponse`, and `capString` (:75) formats it as "64 MiB", "8 KiB" or "N bytes".
- **New types:** `RefusedError`/`Refuse` (:102-115) keep the v1 text `ipc: daemon refused the request: <msg>`. Also new: `BlastView` (:161, with JSON key `error`), `ValidBlastView` (:175), `RebaseResult` (:186) and `Handler` (:195). `getHandler` (:201) answers rebase with code `unsupported`.
- **Wire structs:** `Snapshot` gains `Blast *BlastView` (`blast,omitempty`) after `SARIF` and the unexported `blastLine`. `response` gains `code` and `rebase` after the v1 fields, so the v1 key order is kept.
- **`respond`** (:306): a lenient `struct{V int}` decode and the version check come first. Then `strictRequest` (:348) does the `DisallowUnknownFields` decode, requires `io.EOF` after one value, refuses `expect` on any op but rebase, and compares the line with `json.Marshal(req)` (:362). Plain handler errors become code `internal` with the message "internal error" (:334).
- **`snapshotResponse`** (:371): report gets a struct copy with `Blast = nil`, and blast gets a copy with the four check byte fields nil. The handler's snapshot is never modified.
- **`decodeResponse`** (:398) returns `*VersionError`, `*RefusedError`, `malformed response: no blast view` / `empty blast view` (through `ValidBlastView`) and `malformed response: rebase ok without a result`.

### Task 2: ServeHandler, Seal, Rebase client, cap, dump downgrade, stubs
- **`Seal`** (ipc.go:441):
  - It always re-encodes and never skips because a line is already present (sec #372).
  - Over `responseCap` it replaces `s.Blast` with a copy that has Text/JSON nil and TooLarge set to the encoded size (:449). It never writes through the shared view; TestSealBlast checks the original view is untouched.
  - If encoding fails it stores an Error view.
  - `Sealed()` (:157) is documented as tests-only, because a struct copy reports Sealed with a stale line.
- **`answer`** (:476):
  - It writes a sealed line as is (:478).
  - An unsealed snapshot (the backstop) is encoded per request, and a blast line over the cap becomes `blast view is <n> bytes, over the <cap> response cap; run gruntled blast --base` with code `too_large`.
  - Plain report keeps v1 behaviour: no server-side cap.
- **Errors after the write:** `noReplyError` (:500) keeps the v1 text `ipc: read from <sock>: ...` and matches `ErrNoReply`. `readReply` (:512) names the cap on an over-cap line and wraps `errLineTooLong`, which is not `ErrNoReply`.
- **sock_unix.go:**
  - `Serve` (:108) wraps the getter in `ServeHandler` (:113), and `handle` (:211) calls `answer`.
  - `Query` (:261) keeps its signature.
  - `Rebase` (:270) wraps every post-send failure that is not a `*RefusedError` or `*VersionError` as `ErrOutcomeUnknown` (:281).
  - `exchange` (:298) reports whether the request was written.
- **sock_other.go:** `ServeHandler` (inert) and `Rebase` (`ErrUnsupported`) stubs.
- **dump.go:**
  - `WriteDump` (:26) re-encodes an over-cap dump with a copy of the view without its bytes (:42). The caller's snapshot is unchanged.
  - `ReadDump` (:54) uses `responseCap` and says `dump over the <cap> cap`.
- **Measured:**

| Case | 20 blast requests allocate | sealed line |
|------|---------------------------:|------------:|
| 2 MiB view, in cap | 25,512 B | 2,796,562 B |
| 64 KiB view, cap 8 KiB (too large) | 25,512 B | 352 B |

  - TestCompatV2DaemonV1Request: raw v1 report and ping requests get `v:2, ok:false, unsupported protocol version 1`, the v1 decode sees a mismatch, and `query(request{V:1})` gives `{2,1}`.
- **ipc_test.go:**

## Deviations from Plan

**1. [Signature] decodeResponse returns the rebase result as a fourth value**
- The plan names the function but not its results. Rebase needs the result, so `decodeResponse(line, clientV, op)` returns `(Info, *Snapshot, *RebaseResult, error)`. Query drops the third value.

**2. [Test placement] Non-socket compat tests live in ipc_test.go**
- TestCompatV1Dump, TestCompatV1DecoderRefusesV2Dump and TestReportResponseHasNoBlast need no socket. They are in ipc_test.go, which has no build tag, so they also run on windows. compat_unix_test.go holds the two socket tests. No file outside the plan's list was added.

**3. [Extra tests] TestValidBlastView, TestRespondPassesExpect, TestSealedBlastOverSocket**
- These are small extra tests: ValidBlastView's own table, the max-uint64 and nil expect passed to the handler, and the sealed too-large view over a real socket.

**4. [Interim adaptation] Task 1 touched sock_unix.go minimally**
- respond's new signature had to compile, so sock_unix.go got a two-line adaptation in 5bfbac6. In the same commit TestQueryVersionMismatch became the v1-client case ({2,1}), so every commit compiles and passes. Task 2 then moved that test to the request value.

**5. [Test helper fix] rawServer stop**
- The first run of the Task 2 tests hung: after the listener closed, the accept error was not `os.ErrClosed`, so the helper's loop kept spinning. The helper now stops on a quit channel. This fix went into the feat commit 0b04c38. No production code was involved.
